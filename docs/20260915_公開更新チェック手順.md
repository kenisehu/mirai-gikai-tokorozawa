# 所沢市版：更新・公開・復旧チェック

## 公開の順序

1. 市の議案・審議結果の原文を読む。結果の「可決」「回答」「委員会付託」を混同しない。確認日と資料URLを残す。AIの推測だけで結果を変更しない。
2. DB更新前に対象行（billsのstatus/status_note、municipal_bill_metadataのdeliberation_result、municipal_deliberation_events）を対象会議で絞って取得・保存する。秘密鍵や個人情報は保存しない。
3. `supabase/record-tokorozawa-september-results.sql` は2026年9月14日結果専用。41件・番号の一意性・31件の確定結果・新しい結果がないことを検査する。初回は末尾COMMITをROLLBACKに置き換え、16/13/2/10件になることを確認する。エラーのまま続行しない。
4. コードをテスト・レビュー後に公開し、同SQLをCOMMITで反映。権限・恒久テーブルのRLS設定は変更しない。TEMPテーブルは当該接続内だけに存在する。
5. SQLで永続化した状態を別途読み直す。31件のvoteイベントが重複せず、決算10件が未確定であることを確認。再実行時も同数になることをROLLBACK試行で確認する。
6. VercelでReadyとProductionのドメイン割当を確認。キャッシュは詳細最大10分、トップ最大1時間の設定があるため、新しいデプロイか再検証後に確認する。リロードだけで更新されたと思い込まない。
7. `node scripts/audit-tokorozawa-september.mjs` を実行。現在41件＋主な7ページについてHTTP・結果分類・古い表現・原文/訂正リンク・新解説を確認する。これは9月15日版専用の検査であり、市の将来の公表を自動認識する仕組みではない。会議が変わったら原文を照合して検査条件も更新する。
8. ブラウザーで検索→詳細→原文リンク、一般質問の絞込、過去会議、訂正フォームの必須項目検証を確認。送信の確認は「動作確認」と明記した非個人情報で行い、運営画面での確認を別途記録する。管理者認証がなければ完了扱いにしない。

## 復旧

2026年9月15日の反映前、対象41件をSQLのJSON出力で全件確認済み：全件 `status=introduced`、`deliberation_result=null`、`status_note=bill_number + ' 所沢市議会へ市長提出'`。この3項目はこの規則から更新前の値を復元できる。後日の状態へ無条件に適用しない。

- UI不具合：Vercelの正常だったデプロイを再びProductionへ戻す。Gitは該当コミットのrevertで履歴を残し、無関係な変更をresetしない。
- DB不具合：コードを戻してもDBは戻らない。保存した更新前の行と現在の行を照合して、今回変更した対象・列だけをトランザクション内で復旧する。後日の正しい結果・利用者の訂正投稿は消さない。新しいvoteイベントの扱いは個別に判断し、全削除やseedの再投入をしない。
- 原文の訂正：最新資料を根拠に解説・結果・履歴を更新する。過去の資料確認日を新しい確認日で一律に塗り替えない。
